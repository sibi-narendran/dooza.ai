Loading runner.js, rules.json, fixtures.json…




Expected results sit in fixtures.json and were fixed before the run. runner.js computes the observed result from rules + evidence only, then compares them per case. Click a case for expected vs observed, reasons and lineage.









Evidence rules




Missing evidence → BLOCKED
A required input was never supplied (the question is not in the fixture, the record was not delivered). The runner makes no inference: no Finding, no withholding decision, nothing guessed or filled in. The test is reported as BLOCKED, naming the missing input, its owner and what can still be checked.
Example: P1-C06, occult question absent → blocked on ER-02:occult_involvement.


Negative evidence → WITHHELD
The input was supplied and says no (or is out of scope, or not qualified). That is real evidence. The rule is not met, so the interpretation is correctly withheld, and the test can PASSED by withholding.
Examples: P1-C04 occult answered "no"; P1-C05 illness reported for the participant only, rule needs a family pattern.


Expected (fixed before the run)
Each case's expected block is written from the GSK rule and committed in fixtures.json before anything runs. Its SHA-256 is pinned in the manifest, so a changed expectation shows up as a changed hash.


Observed (runner output)
runner.js never reads expected. It evaluates rules + evidence, then a separate compare() checks six fields per case: disposition, finding type, claim ceiling, support level, rejected claims, blocked-on. Any difference = FAILED with the field named.




Boundaries applied (from the posting's example)
    

  • Qualified family illness pattern + personal/family occult evidence permits a bounded investigation hypothesis about a barrier to healing. Ceiling: bounded_hypothesis.
    • 

  • It never permits a medical cause, a confirmed spiritual mechanism or a ministry priority: these are rejected as prohibited inferences (P1-C02).
    • 

  • A strong ministry recommendation is recorded but does not raise support (P1-C03 equals P1-C01).
    • 

  • A participant-reported concern stays a reported concern, never a diagnosis (P1-C08).
    • 

  • Invalid input is rejected and named, not coerced (P1-C09). An undelivered evaluator is NOT RUN, not passed (P1-C11).


Status order of precedence: NOT RUN (evaluator missing) → INVALID_INPUT → BLOCKED (any required input missing) → WITHHELD (supplied but unmet) → PERMITTED.
